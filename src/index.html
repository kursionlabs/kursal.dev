A checker small enough to run in your head.

kursal is a systems language that compiles to C. A few ideas let a library say who owns a resource and who may touch it, and the compiler holds every caller to it. Each check looks at one function and the signatures it calls, never another function’s body, so you can read code and know whether it will pass.

For a linear type, that is the checker’s whole job: follow each value to the end of the function and see that nothing is still owed. The guide builds up to it from a handle that is just a number.

Resource rules live in comments

Close this exactly once. Don’t touch it after the callee frees it. One writer at a time. Every systems codebase has rules like these, and most of them are written in comments and enforced by whoever reviews the diff.

Checkers that enforce such rules exist, and some are very capable. The cost is that when one says no, working out why can take as long as the bug would have. kursal makes a different trade: fewer rules, each one checked locally, so the answer to “will this pass?” is something you can reach by reading.

The rest of this page is how that works, and what it costs.

Four ideas, each with one job

Linear types

A type whose name ends in ! must be used exactly once, on every path. A forgotten handle and a double close are compile errors, and you can see which values carry an obligation from the type names alone.

Places

A parameter marked & lends the caller’s value for one call. You can look at a resource without giving it up, and there are no lifetimes to infer, because a lend never outlives its call.

Brands and capabilities

A brand names a domain, such as a region of memory or another resource. A capability grants access to it. References are copyable and do nothing alone, which is what lets a graph point at itself, or many readers share a structure, without the checker losing track of who may write.

Contracts

Raw memory and calls into C are marked unsafe, with the promise written beside them. A module states that promise once, hides the representation, and every safe caller inherits it.

Each idea fills a gap the previous one leaves. The guide takes them in that order, starting from a handle that is just a number. What each idea catches lists the errors they produce.

What they look like together

A heap-allocated counter, used from code that contains no unsafe. The module behind new_counter does the allocation and holds the unsafe contract. This is the application side.

fn main() {

let exists 'r. (owner, view, exclusive) = new_counter(10);

The counter’s module hands back three things under a fresh brand 'r. owner is linear, so it must be closed. view is copyable. exclusive is the one right to write.

view.write(&exclusive, 32);

A write needs the capability for 'r. The & lends it for the call and gets it back.

let exists 'q. (root, resume) = exclusive.share();

Sharing consumes the write capability and returns the root of a read tree, plus a receipt for getting the writer back. Nothing can write now, and the compiler knows it.

let exists 'a, 'b. (left, right, join) = root.split();

Two readers, each with its own brand, and a receipt for putting them back.

let a = view.read(&left);
let b = view.read(&right);

Reading needs only a reader. view is the same copyable value in both lines.

let exclusive = resume.resume(join.join(left, right));

The writer comes back only after both readers are joined.

owner.close(exclusive);

Closing wants the write capability back, and uses up the linear owner.

print_buffer(f"{a} + {b}\n");
}

prints32 + 32

Try to close the counter while the readers are still out and the compiler refuses: the write capability hasn’t come back yet. Try to read through view without a capability and there is nothing to pass. The rules that stop you are all in signatures you can see, and none of them needed a lifetime.

The checker is small, and it gets checked

kursal lowers every program to KURS, a small core language in which each block states its complete contract: what is full, what is empty, what is lent. A separate checker re-verifies the KURS before any C is emitted. If the front end breaks one of these rules, the result is “front end accepted, checker rejected”, not a program that runs with the rule broken.

Fuzzed against itself

Thousands of generated and mutated programs turned up cases where the front end accepted what the checker rejected, among them an aliasing hole in f(&x, &x). All are fixed and kept as regression tests. The fuzzer also compares the two compilers and runs sanitizers.

Two compilers

A Python reference compiler and a self-hosted one, kept identical by differential tests. The self-hosted compiler reaches a bootstrap fixpoint: stage 1 and stage 2 emit byte-identical C.

A proof of the design

The soundness of the core’s design rules is proven in Lean, for a single-threaded core without a few extensions such as atomics. The compilers and the checker are not proven, which is why an independent checker re-checks the compilers’ output.

What the core checks, and how to read it by hand, is step 8 of the guide.

Young, and open about it

kursal has not had a 1.0, and breaking changes are expected. It targets Linux, compiles through a C compiler, and has no package manager yet. Some things you might expect are not there. Why kursal says plainly what you give up, and the repository tracks what is supported today.
